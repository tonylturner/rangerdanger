## Compose delivery options (I unless explicitly marked V)

Assume **serial selection, not concurrent packages**. No option itself solves loader/global IDs, command targets, proxy upstreams, routing or persisted state. All need one active-package contract consumed outside Compose. Comparison is against observed call sites above; no prototype was implemented.

| Option | Setup/dev | SSD/delta/release | CI / frozen-behavior impact |
|---|---|---|---|
| **Per-package fragments via `include`** | Dispatcher must select only one fragment; `include` requires Compose >=2.20, beyond setup's generic V2 check (`setup.sh:102-105`, PS `:90-94`). Include handles independent file-relative bases but variable/project/path behavior must be pinned and tested. Common service names must not collide across includes; include is not an override mechanism. | Stage must enumerate each selected combination, archive every included bind asset, freeze package selection and override *its* images offline. Guard's literal root scan misses included images. Generated delta recipes still choose US files. | Package combinations + minimum Compose version test needed. Extracting common platform changes frozen US file organization; retaining legacy files avoids that but duplicates authority. ## Shipping more than one package: concrete release/SSD obligations (I)

- **Separate three catalogs:** (a) first-party build recipes/input envelopes/platforms, (b) package->service->runtime image refs incl. external containd/nginx/alpine/helpers, (c) immutable per-release/per-package resolution records incl. asset/manifest hashes. Extend guard from one literal release YAML to resolved catalog union, and keep completeness checks against planned inventory (`release.yml:842-915`).
